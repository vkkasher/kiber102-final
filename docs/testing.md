# Проверки

Команды выполняются из корня проекта. Примеры Python ниже для Windows, на Linux путь интерпретатора заменяется на `.venv/bin/python`. Тестовые записи создаются только в изолированных базах.

## Регрессии диалога и сообщений Telegram

После проверки 15 ноября добавлены `tests/agent/test_dialog_hardening.py`, `tests/agent/test_bot_presentation.py` и `tests/agent/test_bot_pagination.py`, всего 117 случаев. Они проверяют дни недели и следующую неделю, ответы о возрасте и составе группы, самостоятельные запросы без команды сброса, сохранение уточнений, восстановление после старого ошибочного фильтра названия, фактические основания отказа и защиту от неподтверждённых условий модели. Форматирование проверяется на HTML-вставках, длинных строках и Unicode. Статьи проверяются схемой aiogram, фотографии связываются с конкретными событиями и загружаются файлами. Реальные обработчики проверяются через aiogram без сети, включая отказ отправки и неопределённый исход. Пагинация проверяет края двух и трёх страниц, возврат без повторного API-запроса, привязку к пользователю, смену поиска и редактирование исходного сообщения. План из четырёх событий делится на страницы без повторного планирования. Кнопки источника и покупки сохраняют правила API.

Полный прогон после этих изменений: 449 passed, 5 skipped. Дополнительно пройдены 70 внутренних контрольных контрактов, цепочка 13 запросов на изолированной копии реального каталога и 383 календарных и форматных проверки. Эти результаты не заменяют независимую внешнюю приёмку качества модели. Актуальный [отчёт по диалогу и Telegram](evidence/dialog-hardening.json) сохраняется отдельно от первоначального финального аудита.

```powershell
.venv/Scripts/python.exe -m ruff check apps tests scripts
.venv/Scripts/python.exe -m pytest -q
.venv/Scripts/python.exe -X utf8 scripts/generate_api_types.py --check
npm --prefix apps/web run lint
npm --prefix apps/web test
npm --prefix apps/web run build
npm --prefix apps/web run typecheck
```

`POSTGRES_TEST_URL` должен указывать на отдельную тестовую PostgreSQL. Тесты используют случайные схемы, не назначайте им production-базу. Без переменной пять PostgreSQL-проверок пропускаются. Точные результаты текущей подготовки находятся в [приёмке](acceptance.md) и `docs/evidence`.

При финальном аудите пять проверок выполнены на отдельном PostgreSQL 18 с временным кластером, loopback-портом и случайным паролем. После проверки кластер остановлен и удалён. Это проверка SQL, транзакций, миграций и конкурентных операций, но не холодный запуск Compose с PostgreSQL 17.

## Контрольный набор и источники

```powershell
.venv/Scripts/python.exe -X utf8 -m tests.evals.run --include-holdout --output docs/evidence/evaluation.json
.venv/Scripts/python.exe -X utf8 scripts/review_source_quality.py
```

Первый runner использует синтетические fixtures в отдельной БД и по умолчанию отключает модель. Он проверяет 60 основных и 10 внутренних контрольных контрактов с baseline. Эти десять случаев не являются десятью независимыми внешними запросами из PDF. Режим `--with-local-model` допускает только локальный endpoint и не запускает платный OpenRouter.

Второй скрипт сверяет сохранённые исходные байты с SHA256, разбирает адаптеры и сравнивает 50 карточек с разметкой. В метаданных `human_verified=false`. Совпадение 500 полей в этой проверке не заменяет независимую человеческую оценку. Дата снимков важна, текущий сайт источника может уже отличаться.

Платные сетевые smoke-тесты выполняются отдельно с явно ограниченным ключом. Отчёт по пяти репликам DeepSeek сохранён в `docs/evidence/deepseek-dialog.json`. Он не является полным независимым бенчмарком модели.

## Браузер

Инструкция изолированных Playwright-сценариев находится в [apps/web/tests/README.md](../apps/web/tests/README.md). Сценарии изменения событий требуют `ISOLATED_WEB_E2E=1`, отдельного API, отдельной SQLite-БД, отдельных секретов и порта 3100. Читающие тесты можно направить на выбранный запущенный экземпляр через `WEB_TEST_URL`.

Для read-only проверки API есть `python scripts/verify_live.py --help`. Она выполняет поиск и резервные агентские запросы на настоящем каталоге, но не импортирует и не отменяет события. Прогон создаёт обычные трассы и учитывается в HTTP rate limit. Локальные проверки не подтверждают нагрузочную устойчивость, доставку Telegram или приёмку production-экземпляра.

Последний полный браузерный прогон выполняется на production-сборке standalone с отдельными API, БД и секретами. Проверяются публичные страницы, постоянная карточка и 404, все панели модерации, импорт, формы, подтверждения, подписка и удаление, поиск и фильтры, история URL, ошибки сети, iframe, локальный Swagger, клавиатура и ширины 360/390/768/1280/1440 px. Правки реальных событий и рассылки на публичном экземпляре для этого не нужны. Автоматический axe-проход не заменяет ручную проверку всей WCAG.

Зависимости проверяются через `python -m pip check`, `npm audit` и OSV для закреплённых Python-пакетов. В итоговой копии перед публикацией отдельно проверяются все файлы на значения проектных секретов и типовые форматы ключей. Рабочие `.env`, приватные архивы и пользовательские базы исключаются. Обезличенный снимок каталога проверяется после распаковки, пользовательские таблицы в нём пусты. Упаковщик также проверяет исходники на значения текущих проектных секретов. Такая проверка не гарантирует распознавание произвольного пароля в любом тексте. Датированные результаты прошлых проверок сохраняют свою область применимости.
