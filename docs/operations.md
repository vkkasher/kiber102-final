# Эксплуатация

## Проверки и диагностика

Readiness API находится по `/api/v1/health`, метрики текущего процесса по `/api/v1/metrics`. Для диагностики Compose используйте `docker compose ps` и `docker compose logs --tail=100 api web worker bot`. В логах API сохраняются request_id, метод, шаблон маршрута, статус и задержка. Query/body/IP в HTTP access-log не записываются. Перед передачей диагностического файла дополнительно проверьте его содержимое на секреты и частные данные.

Ошибка модели переводит подбор в fallback. Неизвестный маршрут мешает гарантировать переезд, но не отключает каталог. Ошибка источника сохраняет предыдущие данные и не доказывает отмену. Telegram `Conflict: terminated by other getUpdates request` означает вторую polling-копию. Оставьте один заранее выбранный экземпляр, не перевыпускайте токен ради этого конфликта.

## Работа с каталогом

Оператор входит в `/admin`, импортирует CSV/JSON или создаёт черновик, проверяет источник и публикует запись. Отмена меняет статус и сохраняет историю. Не исправляйте даты, цены и возраст предположениями. Для внешнего источника можно отключить сбор через административный реестр. Одиночный сбор выполняется `python -m apps.worker.main --once`, только если другой сбор не идёт.

Изображения из `editorial-images.json` являются отдельным реестром фотографий. Его ручное обновление не заменяет проверку источника события и прав на изображения. Лицензированный постер содержит `poster_url` и `poster_rights`. Дополнительный источник Кассы.ру возвращает отдельные `image_url` и `image_source_url` для точно сопоставленного сеанса. Срок проверки, исходный снимок и сведения о продаже хранятся отдельно от модерации события в `event_ticket_evidence`.

Сборщик работает с интервалом `WORKER_INTERVAL_SECONDS=3600`. Итог прохода находится в `.local/sources/last-report.json`, раздел `ticket_evidence`. Проверяйте `checked`, `matched`, `unavailable`, `errors`. Ненулевое `errors` означает сбой отдельных страниц, а не отмену событий. Подтверждённые недоступные продажи исключаются из общего каталога, который используют сайт, бот, ИИ, планировщик и очередь уведомлений. Изменение подписи в интерфейсе не удаляет данные проверки из API и аудита.

## Резервные копии

Храните отдельно исходники, секреты и рабочие данные. Перед обновлением снимайте PostgreSQL, raw/evidence, состояние бота и конфигурацию. Для SQLite используйте backup API `sqlite3.Connection.backup`, а не копирование открытого файла. Скрипт [package_release.py](../scripts/package_release.py) создаёт согласованный приватный пакет локальной SQLite-базы. Он не заменяет резервное копирование серверной PostgreSQL.

Пример PostgreSQL backup для Bash из папки Compose. Каталог копий должен быть доступен только оператору.

```bash
mkdir -p backups
chmod 700 backups
docker compose exec -T postgres pg_dump -U kiber102 -d kiber102 -Fc > backups/catalog.dump
chmod 600 backups/catalog.dump
```

Восстановление сначала проверяется в отдельной новой БД, без затирания рабочей. Сверьте количество записей, UUID, статусы, источники и административные роли. Копия без успешного тестового восстановления не считается проверенной. Секреты и резервные копии не хранятся в публичном Git или образах контейнеров.

## Обновление

Зафиксируйте используемый commit и образы, выполните backup, проверьте миграции и тесты, затем обновите образ и выполните штатный запуск. После этого повторите readiness и пользовательский сценарий. Откат кода допускается только при совместимости с текущей схемой. Автоматический `alembic downgrade` рабочей базы не является способом обычного отката.

Для SQLite запускайте `python scripts/migrate.py` из корня. Скрипт распознаёт точную схему таблиц, ранее созданную локальным API, и согласует её с Alembic только после проверки колонок, связей, индексов и первичных ключей. При расхождении он останавливается без изменения версии. Миграция `d7f3198a624e` дополняет прежние наблюдения нормализованным временем окончания, сохраняя исходные снимки и время их проверки. Резервная копия перед миграцией обязательна.

## Сроки хранения

| Данные | Срок |
|---|---|
| Трассы, диалоги, подтверждения, денежный учёт и дневные квоты | 30 дней |
| Очередь доставки уведомлений | 30 дней |
| Обращения, raw-данные и снимки источников | 90 дней |
| Подписки и минимальное состояние бота | 180 дней |
| История реплик бота | Сбрасывается после 30 дней неактивности |

Очистку БД вызывает служебный maintenance, worker также удаляет истёкшие исходные файлы. Сроки не ограничивают автоматически срок отдельного операторского backup. Его регламент задаёт владелец экземпляра. Принудительный сброс состояния посетителя не обнуляет серверный денежный лимит.
